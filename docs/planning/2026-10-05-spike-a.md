# Spike A: DuckDB and server facts on this laptop

Run on 2026-10-02, ahead of the 2026-10-05 spike milestone. It settles the facts in design §20
that slice 1a's SQL runner depends on (Tasks 11-17).

**Result:** the runner design holds.
- Three of the plan's probes failed: P1, P4 and one of P7's twelve escape attempts. Each has a
  working replacement, and each changed the design in place, marked "(amended 2026-10-02 after
  spike A)".
- The extra probes found code in the plan that would not work as written: X5a, plus items 2, 5,
  6 and 13 under "For Tasks 11-17". None of these changes the design.
- One exploration script made an unapproved download: the DuckDB ICU extension, about 28 MB. See
  "Network use during this spike". It does not change any conclusion, and item 17 stops it
  happening again.

## For Tasks 11-17

**API names in `@duckdb/node-api` 1.5.6-r.1.** Every name the plan uses exists:
- the instance: `DuckDBInstance.create(path, options)`, `instance.connect()`,
  `instance.closeSync()`;
- the connection: `connection.disconnectSync()`, `connection.interrupt()`,
  `connection.extractStatements(sql)`, then `.count` and `.prepare(index)`;
- the prepared statement: `prepared.statementType`, `prepared.columnCount`,
  `prepared.columnName(i)`, `prepared.columnType(i).toString()`,
  `prepared.streamAndReadUntil(n)`, `prepared.runAndReadAll()`,
  `prepared.bindVarchar(1, text)` (the index starts at 1);
- the result reader: `reader.getRowsJson()`, `reader.columnNames()`,
  `reader.currentRowCount`, `reader.done`;
- `StatementType.SELECT` and `DuckDBTimestampTZValue` are imported from `@duckdb/node-api`.

One more is available: `connection.getTableNames(sql, true)` returns the tables a query names, as
strings like `edge.t`.

**Fallbacks and fixes in force:**

1. **Opening the runner (Task 11).** Do not pass `TimeZone` or `lock_configuration` to
   `DuckDBInstance.create`. Pass the other eight options in their order. Then use a setup
   connection, close it, and only then accept requests:

   ```ts
   const inst = await DuckDBInstance.create(dbPath, {
     access_mode: 'READ_ONLY', temp_directory: '', threads: '2', memory_limit: '1GB',
     autoinstall_known_extensions: 'false', autoload_known_extensions: 'false',
     allow_community_extensions: 'false', enable_external_access: 'false',
   });
   const setup = await inst.connect();
   await setup.run(`SET GLOBAL TimeZone = 'UTC'`);
   await setup.run(`SET GLOBAL lock_configuration = true`);
   setup.disconnectSync();
   ```

   `temp_directory` must still come before `enable_external_access`. The other order fails with
   `Failed to set config`. The order list in `global-constraints.md` and the plan's
   `INSTANCE_OPTIONS` need the same change.
2. **TIMESTAMPTZ text (Task 11).** Set `DuckDBTimestampTZValue.timezoneOffsetInMinutes = 0` once,
   when the child process starts. The default is the laptop's offset, so a UTC noon prints as
   `14:00:00+02`. The plan's `child.ts` does not set it yet.
3. **The parse tree (Task 11).** Prepare `SELECT json_serialize_sql($1::VARCHAR)`, not `($1)`.
   The plan's version throws at prepare. Its `.catch(() => tablesFromText(sql))` would hide that
   and quietly use the weaker text check every time. Treat a reply with `"error": true` as a
   failure as well. Keep `useParseTree: true`.
4. **What each table check catches (Task 11).**
   - The parse tree catches every schema-named table tried, including comma joins, subqueries,
     CTEs, DESCRIBE, SUMMARIZE, SHOW and PIVOT.
   - The text regex misses comma joins (`FROM t, edge.t`) and the DESCRIBE, SUMMARIZE, SHOW and
     PIVOT forms, so it is only a backstop.
   - Neither sees a table named inside a string, as in `query_table('edge.t')` or `query('...')`.
     The function denylist stays. `getTableNames(sql, true)` does catch these, and could be
     added as a cross-check.
5. **Empty input (Task 11).** `extractStatements` throws `Error in native callback` for empty,
   blank and comment-only text. Check the masked text (`maskSql(sql).trim() === ''`) before
   extracting. The plan's `!sql.trim()` misses comment-only text. `SELECT 1; -- done` and
   `SELECT 1;;` extract as one statement.
6. **The deadline covers the gate too (Tasks 11-12).**
   - DuckDB works out constant expressions while preparing. One heavy expression spent 5.5
     seconds in `prepare`. In the plan's code, that time falls before the deadline starts.
   - Start `withDeadline` before `extractStatements`.
   - `interrupt()` does reach a prepare: a large `repeat()` stopped at 340 ms. But a single long
     function call only notices once it returns.
   - Task 12's kill at deadline plus grace is the real limit for that case, and it already
     covers the whole request.
7. **Statement types (Task 11).**
   - Pass the SELECT check: plain SELECT, WITH, VALUES, UNION, FROM-first, DESCRIBE, SUMMARIZE,
     SHOW, UNPIVOT, and PIVOT with an `IN (...)` list. Their schema-named tables are caught by
     item 4.
   - **PIVOT without an IN list** splits into 2 statements, so it is rejected as "one statement
     only". A clearer message would help, if PIVOT is ever taught.
   - Rejected as `not_select`: EXPLAIN, CREATE, INSERT, DROP, SET, PRAGMA, CALL and ATTACH. They
     prepare and report their own type.
   - COPY ... TO is different: it throws a Permission Error at prepare, so it comes back as an
     engine error.
8. **Where errors appear (Tasks 11 and 14).**
   - At extract: syntax errors, as `Parser Error: syntax error at or near ...`.
   - At prepare: unknown column, unknown table, a GROUP BY error, an ambiguous column, an
     aggregate in WHERE and `'a' + 1`. They come as `Binder Error` or `Catalog Error`.
   - At run: `Conversion Error`, even for a constant `CAST('x' AS INTEGER)`.
   - No error: `1/0` gives Infinity, and `1//0` gives NULL.
9. **Interrupts (Tasks 11-12).**
   - Wherever a query reached the deadline, the first `interrupt()` usually stopped it. In X3 it
     stopped 6 of the 9 shapes, 3-13 ms after it was sent, through both `streamAndReadUntil` and
     `runAndReadAll`. In P9 it stopped all 3, 2-14 ms after it was sent.
   - The other three X3 shapes:
     - a sort over a cross join ran on about 99 ms after the interrupt, until the memory limit
       stopped it;
     - a `string_agg` runaway hit the memory limit before the deadline;
     - one huge `regexp_replace` call did its work in prepare (item 6).
   - Only one interrupt was sent in each X3 case, so the repeat was never needed here. Task 11's
     deadline test covers the repeat with a fake connection.
   - The connection is reusable afterwards. No other query shape is needed for the runaway
     tests.
   - The plan's P9 left its repeat timer running for 5 seconds. X3, which clears the timer, is
     the cleaner measure.
10. **Display cap (Task 11).** `streamAndReadUntil(1001)` returns whole chunks (2,048 rows). The
    plan already slices to the cap and uses `rows.length > cap` to flag truncation.
11. **Memory (Task 12).** The 1 GB limit stops a runaway in under a second with no paging. The
    connection is reusable afterwards.
12. **Comparison facts (Task 13).**
    - NULL matches NULL in EXCEPT ALL. `NaN = NaN` is true.
    - `'1'` matches `1`, and DATE matches a midnight TIMESTAMP, after an implicit cast. The
      type-class check before comparing (design §6, step 3) is therefore required, as planned.
13. **Column type strings (Task 13).**
    - TIMESTAMPTZ reads as `TIMESTAMP WITH TIME ZONE`, REAL as `FLOAT`, and a list as `INTEGER[]`.
    - A bare NULL column reads as `INTEGER`.
    - `sum` of `DECIMAL(10,2)` gives `DECIMAL(38,2)`, and `avg` of a DECIMAL gives `DOUBLE`.
    - `7/2` is DOUBLE and `7//2` is INTEGER.
    - The plan's `typeClassOf` handles all of these, with one exception. **INTERVAL** matches its
      numeric regex, because `INT` is a prefix of `INTERVAL`, so it would be classed numeric. X2
      produced an INTERVAL column. Task 13 must class INTERVAL as `'other'`, for example by
      testing for it before the numeric regex, and add a test for it.
14. **JSON values (Tasks 11, 13, 15).** BIGINT, HUGEINT, UBIGINT, DECIMAL, DATE and TIMESTAMP
    arrive as strings. INTEGER and finite DOUBLE arrive as numbers. NaN and infinity in a DOUBLE
    arrive as the strings `"NaN"` and `"Infinity"`.
15. **Self-checks (Task 17).**
    - Use `SELECT list(DISTINCT function_name ORDER BY function_name) FROM duckdb_functions()
      WHERE function_name IN ('json_serialize_sql', 'icu_sort_key')`, plus
      `current_setting('TimeZone') = 'UTC'`.
    - The plan's "JSON is not loaded" fallback does not apply. ICU and JSON are both statically
      linked and loaded. The review probe (R1) saw both as `STATICALLY_LINKED` with the extension
      folder pointed away, so no downloaded file was involved.
    - `pragma_version()` gives `library_version` `v1.5.6` (with the `v`) on both sides. Python's
      `duckdb.__version__` is `1.5.6` (without it). The manifest should record Python's
      `pragma_version()` value so the strings match.
16. **The server address (Task 17).**
    - Binding `127.0.0.1` gives a single IPv4 listener. `[::1]` is refused, so
      `http://localhost:5174` only works through the browser's fallback to IPv4.
    - Print `http://127.0.0.1:5174` as the address to open.
    - DuckDB loading at all proves the VC++ runtime is present. The registry key above is
      another way to check.
17. **Every unlocked DuckDB instance (all tasks).** Test fixtures, scripts and tools must not
    download extensions:
    - Pass `autoinstall_known_extensions: 'false'` and `autoload_known_extensions: 'false'` at
      creation.
    - Set TimeZone with `SET` after opening, never at creation.
    - This covers `tests/helpers/fixture-db.ts` (`makeFixtureDb`), which the plan opens with no
      options at all.
    - Nothing needs loading: ICU and JSON are statically linked (review probe R1).
    - With TimeZone at creation and autoinstall on, DuckDB downloads ICU from
      extensions.duckdb.org. A query that names an extension that is not built in, such as
      `httpfs`, would do the same. See "Network use during this spike".

**For other slices:**
- Every unlocked DuckDB instance, including the Python pipeline, follows item 17. In Python, open
  with `config={'autoinstall_known_extensions': False, 'autoload_known_extensions': False}`, then
  run `SET TimeZone = 'UTC'`. Y1 checked this: the Python wheel also has ICU and JSON statically
  linked, and the `SET` works with autoload off.
- Pipeline: a view body that names its table without a schema reads its own schema (X0b).
  TEMP tables work on the read-only file (X7).
- Slice 3: a second locked runner with `integer_division=true` works (X9), so the re-run that
  gives an exact integer-division note is possible.
