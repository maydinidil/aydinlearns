# Spike 1b: ts-fsrs 5.4.2 on this laptop

Run on 2026-10-03, for Task B1 of the sprint 2 plan. It settles the scheduler facts in design §20
that slice 1b's scheduler (Task B3) and replay (Task B6) depend on.

**Result:** the scheduler contract holds as planned. The `CardSnapshot` field list, the parameter
names, the retrievability call and Task B3's imports are all confirmed, and replay with fuzz on is
deterministic. One probe failed:
- **P4, the 180-day maximum.** When the cap binds, ts-fsrs keeps Hard at 180 days but gives Good
  181 and Easy 182. Task B3 must not test "at most 180" for Good and Easy, unless the controller
  chooses to clamp (see "The 180-day maximum").

Two design §20 facts need a small correction: a Good moves difficulty by about 0.01 rather than
leaving it unchanged (X2), and retrievability counts whole 24-hour periods, not UTC dates (X3).

## The fuzz seed

ts-fsrs seeds the fuzz at each review from three values: the review time in milliseconds, the
card's review count including this review, and its difficulty times its stability before this
review. The function is `DefaultInitSeedStrategy` in `node_modules/ts-fsrs/dist/index.mjs`, which
the P1 INFO line names. None of the three is the wall clock or a random source. The generator
falls back to `Date.now()` only when the seed is missing, which the default strategy never
allows. So the same history always gives the same intervals (P1, X6, X7).

The seed changes with every millisecond of the review time: reviews 1 ms apart gave intervals
from 45 to 53 days. Live scheduling and replay must pass exactly the same timestamp.

## The 180-day maximum

ts-fsrs caps each rating's interval at `maximum_interval`, then makes Good at least one day longer
than Hard and Easy at least one day longer than Good. When the cap binds, Hard stays at 180, Good
becomes 181 and Easy 182 (X1). This happens with fuzz on and off.

So design §5's 180 days holds for Hard only. Good and Easy can run one or two days over. With Easy
at every review, a card first studied today could get its first such interval in mid-December
2026 (X1b). The extra days come on a due date six months out.

The choice, for the controller:
- **A (recommended): accept it.** Task B3 uses ts-fsrs's interval as given, and its tests expect at
  most 180 days for Hard, 181 for Good and 182 for Easy. Design §5 or §20 records the fact. The
  snapshot stays exactly ts-fsrs's card, so the startup snapshot check (S2-15) needs nothing
  special.
- B: clamp in the wrapper. `reviewCard` cuts `scheduled_days` to 180 and sets `due` to the review
  time plus 180 days. It stays deterministic, but the snapshot then differs from ts-fsrs's own card,
  and Good and Easy give the same interval at the cap.

## What Task B3 must do

- Build the parameters with every preset value set explicitly (P4), `enable_short_term: true` for
  the 15-minute steps, and the default weights from `default_w`. It is exported as a frozen array,
  so copy it: `[...default_w]`.
- Ask for retrievability with `get_retrievability(card, at, false)` (P6). Without `false` it
  returns a percent string. It returns 0 for any New card, so also for a card just reset. It
  counts whole 24-hour periods since the last review, not UTC dates (X3).
- Create one ts-fsrs instance per parameter set and switch between them per review (P7). Sharing
  an instance across cards is safe (X7).
- Fill `CardSnapshot.elapsed_days` itself, as UTC calendar days since the previous review (P2).
  ts-fsrs 5.4.2 already writes the same value to `card.elapsed_days` (X8), so copying and
  computing agree; computing keeps working once ts-fsrs 6.0 drops the field. Any Card the wrapper
  builds must still carry `elapsed_days`, because the 5.4.2 Card type requires it (P9's negative
  control).
- Refuse a review timed before the card's last review with a RangeError (P8). ts-fsrs accepts one
  on the same UTC date silently and moves `last_review` back. It throws its own
  `FSRSValidationError` only for an earlier UTC date (X4).
- Not test "at most 180 days" for Good and Easy (P4, X1), unless the controller picks option B.
- Not test that a Good leaves difficulty exactly unchanged: it moves by about 0.01 (X2).
- No change to the `CardSnapshot` field list or the imports: P0 and P9 confirm them as planned.
  Two optional simplifications:
  - the snapshot can go to `next()` and `get_retrievability()` as a ts-fsrs `CardInput`, with no
    conversion to Date objects (X5);
  - step literals written inline, such as `['15m']`, type-check without the `as unknown as` cast.
    The cast is still needed for `DeckPreset`'s steps, which are typed `string[]`.

## What Task B6 must know

- A reset is an empty card at the `card_event` time (P3); lapses restart at 0, so the leech rule
  counts lapses since the last reset (S2-27). Four lapses took 9 reviews here, because one Good in
  relearning returns a card to review.
- Good on a new card goes straight to review, due in 2 days (1 day at the GA4 boost's 0.93), with
  no 15-minute step (P4, X10). Only Again (15 minutes) and Hard (23 minutes) put a new card in
  Learning, so only those bring a just-rated card back in the same session (S2-34).
- Replay must feed reviews in time order (P8). ts-fsrs itself catches an out-of-order review only
  when it falls on an earlier UTC date (X4).
- The review time passed to ts-fsrs must be the logged timestamp (S2-04), to the millisecond, both
  live and in replay: the fuzz depends on it (P1).
- Logged `card_reviews` snapshots survive JSON exactly (X5), so the startup snapshot check (S2-15)
  can compare them field by field.

## For Tasks B5 and B13

- `elapsed_days` counts UTC days. That is what Retained's "21 UTC days" asks for (S2-26). The
  rules that use Amsterdam dates (Mastered's days, demotion, the daily cap, "due tomorrow") must
  use `local_date`, never `elapsed_days`: around 2026-10-25 the two disagree in both directions
  (P2's last two rows).
- Retrievability only changes once per 24 hours since a card's last review (X3). The composer's
  "lowest retrievability first" should break ties in a fixed way, for example by due date and then
  card ID, so Today's order is stable.

## Not covered

- Fitted weights and the optimiser: design §5 keeps the default weights until applications are
  under way. A `config_change` that carries weights is refused (S2-13).
- Time-target recalibration (after about 2 weeks of use).
- ts-fsrs's `reschedule()` and `rollback()`: replay uses `next()` only.
