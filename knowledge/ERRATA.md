# ERRATA: corrections and owner decisions for the knowledge bank

The research files in `knowledge/` (00 to 10, the README and `review_2026-09-30.md`) are the record
and are never edited. This file records every correction to them and every owner decision that
overrides them. The build tools apply it and cite entry IDs (for example `curriculum.json` lists
`OD-CTE-01` and `OD-DATE-01` in `errata_applied`). Later content is built on it.

Written in slice 0 (design §12, §16) on 2026-10-02. The approved design is
`docs/superpowers/specs/2026-10-01-aydinlearns-v1-design.md` ("design §N").

## How to read it

Every entry is a row in a table with the header below. `tools/check-errata.ts` checks that every
review decision (#1 to #18), every planning-read issue (1 to 101) and every required owner-decision
ref has an entry, and that IDs are unique.

| Column | Meaning |
|---|---|
| ID | `OD-*` for owner decisions; `E-001` upward for fixes, rejections and deferrals |
| Type | `owner_decision`: the owner's choice replaces a bank rule. `fix`: confirmed and corrected, the Action says how. `rejected`: not acted on, with the reason. `deferred`: adjudicated in the slice named |
| Source | The bank file or files concerned, by number (01 is `01_sql_curriculum.md`) |
| Ref | What the entry answers: `review #N` (review decisions), `issue N` (`docs/planning/2026-10-01-knowledge-read-issues.md`), or a bank rule or item. Several refs are separated by `; ` |
| Summary | The problem, in one line |
| Action | What the build does instead, with the design section that applies it |
| Slice | When it takes effect: `0`, `1a`, `1b`, `2a`, `2b`, `3` to `7` (design §16), `3+` (slice 3 or the later slice the plan assigns), `after-apps` (after the first applications), `post-v1`, `tune-up` (the weekly tune-up, built once 2 to 4 weeks of log exist), `none` |

**How the planning-read issues were adjudicated.** Issues that touch slices 1-2 or the schemas
(01 levels 1-2, 02, 05 Voltmarkt, 06 and 10, 04 metrics) were checked against the cited source
lines and decided as `fix` or `rejected`. Issues 97 to 99 come from 08 but touch slice 1a and 1b
features (the diff, the log backup, Today), so they were adjudicated too. Every other issue is
`deferred` to the slice that will adjudicate it; where the design already names the fix, the
Action records it so that slice starts from it. An out-of-scope issue is `rejected` only where the
evidence shows no defect (issue 101). Facts marked "checked on 1.5.6" were run on 2026-10-02 on an
in-memory DuckDB 1.5.6 (the pinned `@duckdb/node-api` 1.5.6-r.1) with
`autoinstall_known_extensions` and `autoload_known_extensions` set to false.

`COR-NN` is correction #NN in 10's corrections table. Question IDs are written as in the bank
(`Q-GA4-39`); E-121 sets the 3-digit form.
